# opus-5-required

> Claude가 반박을 어디서 멈출지(검증 가능 영역 vs 사용자 고유 영역)와 역할 범위를 넘지 않는 기준을 정해 주는 Claude 스킬

## 왜 만들었나
코드로 확인한 반박은 실제로 큰 도움이 됐다. 다른 개발자가 "구현 완료"라고 한 기능이 레포에 없다는 것을 잡아낸 적도 있다.
그런데 팀 일정이나 다른 직군의 작업 계획처럼 AI가 확인할 수 없는 일까지 며칠 전 대화를 근거로 재차 반대하거나, 백엔드 API 명세에 프론트엔드 구현 순서와 체크리스트를 써 넣는 일이 생겼다.
반박의 가치는 살리고 월권은 막기 위해 두 영역을 나누는 기준을 만들었다.

## 언제 쓰나
이 스킬은 특정 문장에 반응하는 스킬이 아니라, 모든 작업 전에 확인하는 기준이다. 특히 이런 상황에서 효과가 크다.
- "FE에서도 이 필드 없앨 거니까 서버에서 거부해도 돼"처럼 사용자가 이미 방향을 정했을 때
- "이번 주 배포 순서는 이렇게 갈게"처럼 팀 일정·조직 사정이 얽힌 판단일 때
- "API 명세 써줘"처럼 다른 직군에 전달할 산출물을 만들 때
- 설계 검토·구현 조언에서 AI가 사용자 결정에 반대 의견을 낼 때

## 무엇을 하나
- 우려를 A(코드·로그·문서로 검증 가능)와 B(일정·인력·조직·타 직군 판단 등 사용자 고유 영역)로 나눈다
- A영역은 사용자가 반대해도 파일·라인·로그 근거를 들어 다시 말한다. 근거 없이 우기지 않는다
- B영역은 사실과 리스크만 한 번 알리고, 답을 받으면 같은 우려를 다시 꺼내지 않는다
- 며칠 전 들은 사정으로 현재 계획을 단정하지 않고 물어본다
- 역할 밖 산출물(상대 직군의 구현 순서·화면 설계·작업 체크리스트)을 만들지 않는다
- 사용자가 결정하면 미련 남기는 문장 없이 그 전제로 바로 구현한다

## 출력 예시
```
좋음: "현재 앱은 이 필드를 항상 전송합니다(OrderForm.dart:42). 이대로 서버가 배포되면 400이 납니다. 배포 순서를 어떻게 맞출까요?"
나쁨: "그러니 값 비교 방식으로 가야 합니다." (판단까지 대신함)
```
